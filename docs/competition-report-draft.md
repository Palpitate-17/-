## 摘要

网站巡检需持续发现内容变化、敏感信息误发布和配置异常，人工逐页检查难以稳定复测。本作品实现了一个离线网站安全巡检最小可行原型：在严格限定的自建本机演示站内读取页面，按规则识别虚构敏感字段并脱敏，使用摘要记录页面内容变化，用 curl 检查响应头，再由本地 API 将结果交给恒脑生成报告。原型保存前次结果作为基线，区分当前命中、规则不再命中和内容变化，并为每类结果保留待核实状态及条件式建议。测试中，首次巡检读取三个页面并得到一条模拟发现；修改演示文件后复测，该发现不再命中且记录一次内容变化。所有目标和数据均为本地虚构演示材料；本作品当前验证的是巡检、比较和解释链路，不对真实业务网站作风险结论。

## 第一章 作品概述

### 1.1 背景与目标

面向企业命题“网站安全智能巡检智能体”，本作品聚焦可重复的巡检闭环：限定目标和路径、采集本机网页、输出脱敏证据、对比前次结果、生成可解释的复测报告。当前阶段的目标是证明端到端链路可运行并可复现。没有取得真实网站授权，因此演示范围固定为自建的 `http://127.0.0.1:8765/`。

### 1.2 当前边界

原型只接受 `127.0.0.1` 的 HTTP 根地址及策略文件中列出的路径，最多读取 10 个页面、单页 256 KiB，不跟随外部链接。`simulated=false` 表示程序实际请求了本机 HTTP 服务；`data_kind=synthetic_local_demo` 表示被访问的内容仍是虚构测试数据。当前没有真实站点授权测试、主动漏洞验证或真实风险评级。定时巡检只在本机进程运行期间有效；Cloudflare Quick Tunnel 仅用于临时演示访问。

## 第二章 作品设计与实现

### 2.1 整体流程

`自建演示站 → 本地巡检程序 → 基线/历史与结构化 JSON → 本地 API → 临时 HTTPS 隧道 → 恒脑工具节点 → 模型整理节点 → 结束节点`

本地巡检程序负责采集与规则判断，模型节点只按字段整理报告，不独立验证漏洞。API 的 `/scan` 需要 `X-API-Key`，并要求请求目标与策略文件完全一致；`/health` 仅用于连通性检查。

### 2.2 功能模块

1. **范围约束与页面发现**：策略文件定义唯一目标、精确允许路径、巡检间隔和敏感字段正则。解析站内链接后只读取允许路径；拒绝外部目标。
2. **规则发现与脱敏**：在本地文本和 HTML 中匹配测试字段，输出 `category`、URL、`evidence_masked`、`verification=pending` 和 `severity=pending`。相同规则在同一 URL 多次命中时只保留一条。可能影响和修复建议都带有“核实后”的条件。
3. **内容完整性对比**：保存文本 SHA-256 摘要作为基线，复测时分别输出 `findings`、`resolved_findings` 和 `changes`。`resolution_status=rule_no_longer_matched` 只表示本轮未再命中；哈希变化只说明内容不同，不证明未授权篡改。
4. **外部工具编排**：使用开源 curl 对本地首页发起 HEAD 请求。若未见 `X-Content-Type-Options`，记录为待核实的被动配置观察，不列为已确认漏洞。原始响应头仅保存在本机被 Git 忽略的文件中。
5. **结果呈现与联调**：生成 JSON、HTML 报告和只含数量统计的历史记录。恒脑工作流通过 API 工具读取 JSON，并按提示词区分当前发现、已消失、内容变化和配置观察。

### 2.3 数据与安全控制

演示配置中的 `api_key=DEMO-ONLY-12345` 是虚构标记，巡检结果只保留 `api_key=[REDACTED]`。API 密钥由本机随机生成，存入 `.local-api-key`，不纳入版本库。对外部网络的临时隧道只转发到本机 API；API 自身仍只读取固定本机演示站。原始响应头、基线、巡检结果和历史记录均为本机生成文件，不作为真实站点检测证据。

## 第三章 作品测试与分析

### 3.1 测试环境和数据

测试站由 Python 标准库 HTTP 服务在 `127.0.0.1:8765` 提供，包含首页、`/about.html` 和 `/public/config.txt` 三个路径。配置文件的敏感字段是人工写入的虚构标记。巡检 API 位于本机 `127.0.0.1:8001`，curl 进行 HEAD 响应头检查；恒脑工具通过临时 HTTPS 隧道调用 API。测试命令和复现步骤见 `docs/portable-setup.md`。

### 3.2 首次巡检与复测

| 指标 | 首次巡检 | 修改配置文件后复测 |
| --- | ---: | ---: |
| 本机读取页面 | 3 | 3 |
| 当前规则发现 | 1 | 0 |
| 本次规则不再命中 | 0 | 1 |
| 内容变化 | 0 | 1 |

首次在 `/public/config.txt` 产生一条 `sensitive_exposure` 模拟发现，证据为 `api_key=[REDACTED]`；`verification` 与 `severity` 均为 `pending`。将文件改为 `# Local demo: issue removed` 后复测，原发现转入 `resolved_findings`，并记录该文件摘要变化。此处“消失”不能等同于真实系统已修复，文件仍可能返回 HTTP 200；本次只移除了虚构标记。

### 3.3 自动验证

`tests/check_local_api.py` 在临时目录中启动自建 HTTP 服务和 API，检查无密钥请求被拒绝、非策略目标被拒绝、首次发现、重复命中去重、复测消失、内容变化、历史记录和条件式解释字段。2026 年 10 月 12 日在当前工作目录及独立克隆目录运行，均输出 `Local API check passed`。测试不触及真实网站，也不更改演示中的基线。

### 3.4 结果分析与限制

本地测试证明“发现 → 修改演示内容 → 复测 → 结构化结果/报告”的链路可运行。缺失响应头属于观察，不等于已验证漏洞。2026 年 10 月 12 日更新提示词后，恒脑工作流的首次与复测报告均按 API 原始数组正确归类：首次为当前 1、已消失 0、变化 0、配置观察 1；复测为当前 0、已消失 1、变化 1、配置观察 1。当前 HTML 报告和恒脑报告均应清楚标记演示数据与待核实状态。尚未完成队友在另一台电脑的独立复现。

## 第四章 创新性和特色说明

作品的特色在于将严格的本地范围约束、脱敏证据、基线复测和模型解释放在同一链路中：规则模块给出可追溯的结构化事实，模型模块负责可读表达。当前原型展示了这种分工的可行性，但没有进行同类产品量化对比，也不宣称算法原创或真实站点检测效果。若后续获得明确授权，可在已有范围约束与复测字段的基础上扩展更多被动检查，并建立人工核验和处置记录。

## 第五章 竞品分析

选取两类有公开文档的工具作定位参照，不做未经实测的性能或准确率比较。ZAP 的 Automation Framework 可按计划编排网站爬取、被动检查、主动扫描等作业；Wazuh 的文件完整性监控在主机侧维护基线，并比较文件校验值和属性。两者与本作品所处的层面不同：当前原型从**本地 HTTP 响应**观察有限页面，同时将结果传给恒脑整理。[ZAP 官方文档](https://www.zaproxy.org/docs/desktop/addons/automation-framework/)；[Wazuh 官方文档](https://documentation.wazuh.com/current/user-manual/capabilities/file-integrity/)（查阅日期：2026-10-12）。

| 维度 | ZAP Automation Framework | Wazuh 文件完整性监控 | 本作品当前原型 |
| --- | --- | --- | --- |
| 主要对象 | Web 应用及其请求/页面 | 受监控主机上的文件和目录 | 自建本机 HTTP 演示站的三个允许路径 |
| 已公开的相关能力 | 可配置自动化作业，包括爬取与扫描 | 保存文件基线、按校验值和属性识别变化 | 限定范围读取、虚构敏感标记脱敏、页面摘要对比、复测归类 |
| 本报告验证情况 | 仅据官方文档了解，未安装对比测试 | 仅据官方文档了解，未安装对比测试 | 已在本机和独立克隆目录完成自动检查 |

由此可见，原型的主要价值是把演示场景的规则事实、复测状态和模型解释串联起来，并明确“待核实”的证据边界。它不是 ZAP 的漏洞扫描替代品，也不具备 Wazuh 的主机文件监控能力。后续若取得明确授权和资源，可评估接入既有工具输出；本次报告不把未实现的接入写成现有功能。
